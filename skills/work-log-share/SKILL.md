# Work Log Share

讓未來的自己或接手的 AI 知道：做了什麼、為什麼這樣做、哪些路已經走不通、從哪裡繼續。輸出是普通 Markdown 檔，不需要特定筆記軟體或外部服務。

## 存在哪裡

- **一律存在 `~/.claude/worklogs/`**（Windows 是 `%USERPROFILE%\.claude\worklogs\`），不存進專案目錄。日誌常含主機、IP、帳號、客戶名稱，放在專案底下會跟著 git 進 repo。
- 檔名：呼叫方（例如 context-guard）給了完整路徑就照用，通常是 `<session_id>.md`；沒給時用 `YYYY-MM-DD-主題.md`，日期取本機當天，主題來自內容。
- 不知道 session id 就不要猜。**不能用「最近修改的 session 檔」認領目前的 session，也不能借用其他 session 的 ID 或結論。**
- 檔案已存在且確定是同一個 session 先前寫的：先讀舊內容，合併成一份完整日誌再整份覆寫，全檔只能有一個 `## 恢復會話`。無法確認是同一個 session 時保留舊檔，新檔加簡短後綴。

請求寫日誌就是對這份本機檔案的寫入授權，目錄不存在就建立。

## 固定格式

依序使用下列二級標題，標題不可省略；某段沒有內容就寫「無」。篇幅依工作實際複雜度決定：一次機械操作可以很短，多輪設計或除錯要展開會影響理解的細節。

```markdown
# <主題> 工作日誌

## 目標
## 進度
## 決策
## 刻意不做的事
## 死路
## 剩餘事項
## 恢復會話
```

各段要寫的內容：

- **目標**：使用者真正要完成什麼、怎樣算完成。關鍵措辭會改變任務含義時，保留短原句並註明是誰說的。
- **進度**：做到哪裡、產出了什麼。附可開啟的檔案路徑；程式碼任務附相關 commit 或複核指令。每項主張註明來源：實測（哪個指令、哪段輸出）、使用者報告、推斷。沒跑過的驗證只能寫「待驗證」；指令 exit 0 也只證明它實際檢查的範圍。
- **決策**：遇到的選擇、最後的取捨與依據。使用者拍板、AI 建議、尚未確認的設想要分得出來。
- **刻意不做的事**：看起來像遺漏、其實有明確理由而沒做的事。寫清理由，避免下一個 session 把它「補齊」。
- **死路**：被推翻的假設、試過失敗的做法。寫原本怎麼想、什麼證據推翻它，標明「排除，別再查」。沒有就寫「無」，不要編造轉折。
- **剩餘事項**：把已完成、尚未驗證、真正卡住的分開。寫下一步怎麼推進、要根據什麼證據做哪個判斷；不要只寫「繼續優化」。
- **恢復會話**：放在最後。用自然語言寫成可直接貼進新 session 的啟動指令，讓新 session 只憑這段就能接著做：
  - 目前目標與已確定的範圍邊界；
  - 這份日誌的完整路徑，以及繼續工作真正要讀的少量檔案；
  - 停在哪一步、尚未解決的問題；
  - 下一步動作與判斷依據，尤其是分岔點、踩過的坑、不能重做的失敗嘗試；
  - 必須遵守的約束，以及還要使用者決定的事。

  長度依恢復需要決定，不要為了短而刪掉關鍵判斷。這一段之後不要再接其他 `#` 或 `##` 標題。

## 還原事實的紀律

從目前 session 和明確相關的產物取材料。先用已有的證據；要補缺口時，只讀跟這段工作相關的檔案。

材料沒提到的細節不能補成事實。原始上下文已經遺失的部分，說明遺失範圍、保留可靠的部分，不要用流暢的敘事掩蓋空白。Session ID、標題、時間等後設資料只在有可靠來源時記錄，沒有就寫「未知」。

正常呼叫不代表專案已完成，狀態依實際情況填寫。工作日誌不是第二套任務資料庫。

## 存檔與收尾

- 只完成這份日誌。Git commit、發布、外發都不由這個 skill 觸發。
- 日誌負責交接；要不要把真兇、死路、指令提煉進長期 memory，照使用者的全域守則處理，不在這裡另訂規則。
- 寫入後讀回檔案，確認存檔位置正確、七個標題齊全、`## 恢復會話` 確實寫入磁碟、事實和待辦沒有混在一起。這是驗證日誌本身，不是重跑專案的全部測試。
- 最後回報檔案路徑、實際工作狀態與重要缺口。不要自行執行清理、壓縮或關閉 session，也不要宣稱知道上下文剩餘比例。宿主沒有寫檔能力時，直接交付 Markdown 內容並說明尚未存檔。
